# Hermes 改动验证方法论

> 一句话：**改动落盘 ≠ 生效；生效 ≠ 正确；正确 ≠ 有效。**
> 本文把 5 个真实翻车案例拆开讲，并给出一套「改完就能验」的固定动作。
> 面向：任何在本机（或其它环境）改动 Hermes / cron / 脚本配置的 agent（Cursor、Codex、Hermes 自己）。
> 不含任何凭据；文中命令可直接粘贴。
> 仓库路径：`dickbk/obsidian-clipper-cn-latest` → `docs/hermes-change-verification-20260923.md`
> 相关：[Token 优化](hermes-token-optimization.md) · [媒体采集与瘦身](hermes-media-slim-dedupe-20260923.md) · [ops](ops-hermes-codex.md)

## 0. 为什么需要这份文档

在本机做过的优化里，**至少一半的返工不是因为方案错，而是因为「验证方式错」**：
改了配置以为生效，其实一直是出厂默认值；看了指标以为变好，其实是采样窗口错位；
算了平均值以为下降，其实分母是几周前的历史。这些错误有一个共同点 ——
**它们都会产出「看起来正确」的数字**，所以不会被自动发现，只会被后续的真实行为打脸。

## 1. 五个真实案例

### 案例 A：写了 `threshold: 0.5`，但它从来没生效过

**现象**：配置文件里 `compression.threshold: 0.5` 躺了很久，团队一直以为「阈值设成 50%」。
**真相**：运行时真实值一直是**出厂默认 256,000**（token）。配置项名被写错 / 层级不对，**引擎静默回落到默认值**。
**教训**：配置文件是「意图」，日志/运行时才是「事实」。验证要读**运行时实际值**，不是读配置文件。

```bash
# ❌ 错：读配置文件就宣布生效
grep threshold config.yaml

# ✅ 对：读运行时真实生效值（压缩遥测里带 effective_threshold）
grep -o 'compression attempt telemetry: {.*}' ~/.hermes/logs/agent.log | tail -1 | python3 -m json.tool
```

> **Hermes 本机特例**：直接编辑 `config.yaml` 会被护栏拒绝（*"Refusing to write to Hermes config file…"*）。
> 唯一合法路径是 `hermes config set <key> <value>`；改 `compression.*` 下一条消息即生效。

### 案例 B：把 `API calls: 0` 当成「零消耗证据」

**现象**：cron 报告里 `API calls: 0`，据此判断「这个 job 不花钱」。
**真相**：同一份报告格式里，**另一个明确在跑 LLM 的 job 也报 0** —— 即该字段在这套报告里根本不填。
**教训**：`0` 有两种可能：**真的是零**，或者**该数据源不覆盖这个维度**（空集被渲染成 0）。
先确认字段的覆盖面，再用它下结论。

```bash
# 判据要挑「结构性」字段，而不是「数值」字段：
#   no_agent 型 → 报告里含  **Mode:** no_agent (script)  + 耗时 + Status: silent (empty output)
#   agent  型 → 报告里含  Schedule:  +  ## Prompt  +  ## Response
```

### 案例 C：跨天环比被照读，报出误导性的「-94%」

**现象**：检查脚本拿「今天 vs 昨天」算环比，报出 −94%，看起来效果惊人。
**真相**：两天的**采样窗口不同**（一天的窗口没跑满、另一天含 6 个 cron 批次），比较的是两个不可比的东西。
**教训**：环比先对齐「同日型 + 同窗口 + 同覆盖渠道」；窗口不满就不出环比结论，只报绝对值。

### 案例 D（本轮新增）：**累计均值类指标对近期改动不敏感**

**现象**：把上下文压缩阈值从 256,000 调到 100,000，去看 `main_per_call`（主会话平均单次输入）
—— 基线 192,600 → 今日 174,479，**只动 9.4%**，看不出调参效果。
**真相**：这个指标的**分母是 7 周全部调用**。当天的改动在总量里只占零点几个百分点，**再有效也测不出来**。
**教训**：验收一个改动，必须选**时间局部性好的指标**。累计均值只能看趋势，不能验收改动。
本轮补的口径：

| 指标 | 时间局部性 | 能否验收改动 |
|---|---|---|
| `main_per_call`（累计均值） | 差（7 周） | ❌ |
| 会话按 `started_at` 归日 | 差（主会话起点固定，全部量记在启动那天） | ❌ |
| **快照差分：今天累计 − 上次快照累计** | 好（按天） | ✅ |
| **压缩事件计数 / 压缩后残留** | 好（逐次，带时间戳） | ✅ |

### 案例 E（本轮新增）：**「生效了」不等于「还有优化空间」**

**现象**：阈值 100,000 已确认生效（日志里触发点 = 100,982 / 100,535），但优化收益不及预期。
**真相**：压缩后的**残留量 R ≈ 74,600**（尾部保护 47,000 + 系统侧常驻 27,800），
这是**机制下限**：阈值只要下探到 R 附近就不再产生收益，而压缩触发频率会变成 256K 时的 **7 倍**
（每涨 ~25K 就压一次），**压缩本身的开销吃掉调参收益**。
**教训**：调参前先量出**被调对象的物理下限**。下限决定「这个旋钮还能拧多少」，
比盯着配置文件里的数字有用得多。

### 案例 F（本轮新增）：**告警被业务门控挡住，机制问题全瞎**

**现象**：脚本里的机制级告警（压缩窗口过小、压缩开销占比过高）不触发。
**真相**：告警代码整段写在 `if 今日 cron 用量 >= 阈值:` 里面。
本机把 cron 改成 `no_agent`（脚本型、0 token）之后，**当日用量经常是 0 → 整段告警永不执行**。
**教训**：告警的**触发条件要与被观察对象匹配**。机制级健康（阈值、窗口、残留）与「今天跑了多少量」无关，
不能挂在业务量门控里。

## 2. 固定动作：改完就问四句

任何改动落地后，按顺序问自己这四句，缺一句就不算验完：

1. **落盘了吗？** —— 读回目标文件（内容 + mtime），不是「我写了」。
2. **生效了吗？** —— 读**运行时实际值**（日志、运行时自报、真实行为），不是读配置文件。
3. **方向对吗？** —— 用**时间局部性好**的指标（按天增量、逐次事件），不用累计均值。
4. **有反例吗？** —— 拿**真实数据**跑一遍，数误报和漏报；只看「自测通过」不算。
   > 自测永远通过，因为自测用例是你自己写的。真实数据的误报率才是判据。

### 可复制的验证模板

```bash
# ① 落盘：读回 + 时间戳
python3 -c "import pathlib,os;p=pathlib.Path('目标文件');print(p.stat().st_mtime, len(p.read_text()))"

# ② 生效：读运行时真实值（示例：压缩阈值 + 残留）
grep -E "context compression (started|done)|Compression budget rearmed" ~/.hermes/logs/agent.log | tail -5

# ③ 方向：按天增量（快照差分），一次写入、次日生效
python3 scripts/token-daily-check.py            # 输出「主会话按天增量」

# ④ 反例：把真实数据灌进去数误报/漏报（示例：判重 8 条真实样本）
python3 scripts/media-dedupe.py --check --title "<真实标题>" --duration-sec <秒> --platform <平台>
```

## 3. 协作边界（给外部 agent / 人工）

- **只读侦察优先**：先跑只读命令把「运行时事实」拿到手，再决定改什么。改之前先备份（`.bak-<日期>`）。
- **配置写入走官方入口**：Hermes 用 `hermes config set`；cron 换模型用
  `hermes cron edit <job_id> --model <m> --provider <p>`（工具层 schema 未暴露 model/provider，
  传了会报 `No updates provided.`）。改动前备份 `cron/jobs.json`，改完确认 `schedule/enabled/next_run` 未被顺手改动。
- **状态文件与脚本同权**：判重/口径脚本会把缓存写到 `state/`（如 `state/media-dedupe-dur-cache.json`）。
  这类文件**可以删**，删了会自动重建（会多花几次网络请求）。
- **不要用「产物内容」做 A/B 判据**：带随机性/自适应切分的流水线（见《媒体采集与瘦身工程经验》§5），
  同参数重跑产物就不一样，产物差异不能证明改动有效。
- **待确认项**：本机 `compression.protect_last_n` 从 20 调到 12 后**几乎无效果**
  （残留取决于「最近 N 条消息」的实际大小，本会话单条 turn 很大 → 12 条已占 47K）。
  其它环境若单条消息更小，这个参数会更有效 —— 调之前先量「最近 12 条的平均体积」。
