## 0. 产物形态与落点（先定死，后面都依赖它）

```
videos/<嘉宾>_<主题>_<日期>/     视频 + 音频同目录（不分开存）
assets/<同名目录>/               转写四件套（几百 KB 级）
articles/                        笔记全文（一层到底，不再分类型）
```

**正片 vs 切片（硬性）**：标题含「完整版 / 全集」或 **时长 ≥ 30 分钟** = 正片；
时长 **< 20 分钟** 或标题含「第 N 集 / 切片 / 精华版 / 预告」= 切片；**同嘉宾取最长**。
规则来源 = 生产者要求：*"有些博主会把长视频切成多个短视频，这样我们就只选完整版执行操作。"*

## 1. 抓取

```bash
# 元数据 + 格式清单（不要按「h264」写死格式 ID）
yt-dlp --list-formats "<URL>"

# 需要的配置（本机 ~/.config/yt-dlp/config）：
#   --proxy http://<内网代理>:7890     # 境外站直连不通；国内站直连与走代理几乎零差
#   --js-runtimes node                 # 否则报 WARNING: No supported JavaScript runtime could be found
```

**坑①：B站同一清晰度有多种编码，格式 ID 每期不同。**

| 编码 | 常见格式 ID | 同 852x480 下的体积差 |
|---|---|---|
| AVC (H.264) | `30032` | 基准（最大） |
| HEVC (H.265) | `30033` | −20% ~ −45% |
| AV1 | `100023` | 同上，个别期 `100047`（胡渊鸣期） |

→ **必须每期实查**，不能按 `30032 = h264` 写死。脚本里优先挑 AV1 / HEVC。

**坑②：B站 UP 主投稿列表接口有风控**（返回 `-352`，随后 412）。
走**搜索接口 + author/mid 过滤**兜底。UP 主 mid 是稳定标识（示例：`505301413`）。

**坑③：境外站抓不动先查网络层再查工具。** 本机的表现是 `Page.navigate timed out` /
`CDN command timed out`，看着像浏览器故障，实际是**直连 000（15s 超时）**、走代理 **200（1s）**。
判定方法：

```bash
curl -s -o /dev/null -w "直连=%{http_code} %{time_total}s\n" -m 15 https://github.com
curl -s -o /dev/null -w "代理=%{http_code} %{time_total}s\n" -m 15 -x http://<内网代理>:7890 https://github.com
```

## 2. 体积口径：**不要信 `ffprobe` 的 `bit_rate`**

```bash
# ❌ 不可信（实测报 272 kbps，实际 106 kbps —— 容器里写的是名义值）
ffprobe -v error -show_entries format=bit_rate -of csv=p=0 file.mp4

# ✅ 唯一可信口径
python3 -c "
import os,subprocess
f='文件路径'; size=os.path.getsize(f)
dur=float(subprocess.run(['ffprobe','-v','error','-show_entries','format=duration','-of','csv=p=0',f],
      capture_output=True,text=True).stdout.strip())
print(f'真实码率 = {size*8/dur/1000:.0f} kbps')"
```

## 3. 视频重编（换编码不换分辨率）

**四门禁，缺一不可**：① 分辨率不变 ② 时长不变（±1s）③ 能解码 ④ 体积更小。

```bash
ffmpeg -i in.mp4 -c copy -map 0 out.mp4      # 换容器/流复制，零重编码
ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,width,height,duration -of csv=p=0 out.mp4
```

**实测收益**：11 期 852x480 从 AVC 换 AV1/HEVC —— **1455.7 MB → 948.6 MB（省 507 MB）**。
**副作用为零**（编码换掉不改内容，与转写无关）。
> 早期我按「编码换掉会不会影响别的东西」犹豫过；结论是**视频重编是绝对安全的**，
> 真正有副作用的是音频（见 §5）。

## 4. 音频瘦身

**关键事实：Whisper / CAMPPlus 的输入恒定是 16 kHz 单声道。** 采样率再高、声道再多，
模型都会先重采样丢信息 → 存 44.1 kHz 立体声纯属浪费空间。

规格：**16 kHz / 单声道 / 32 kbps**（语音场景足够）。

```bash
ffmpeg -i in.m4a -vn -ac 1 -ar 16000 -c:a libmp3lame -b:a 32k out.mp3
# 验证规格（不是验证时长/内容）
ffprobe -v error -select_streams a:0 -show_entries stream=sample_rate,channels -of csv=p=0 out.mp3
```

**实测收益**：16 期 **1384.2 MB → 342.9 MB（省 1041 MB）**；单体幅度 **69% ~ 81%**
（例：54.8 MB → 32 kbps 15.5 MB（−72%）/ 24 kbps 11.7 MB（−79%））。

## 5. ⚠️ 转写产物**不可复现** —— 这是最容易做错判断的地方

**现象**：音频瘦身后，用**同参数**重跑转写，与库内已定稿的转写稿比对 ——
**1377 行不同，占 54%**。

**根因**：转写流水线开了 VAD 切分 + `condition_on_previous_text`。
- VAD 切点会随音频的细微差别（重采样、码率、静音阈值）**漂移**；
- `condition_on_previous_text=True` 让**上一段的输出成为下一段的上下文** →
  一个切点偏移会被**逐段放大**，形成级联差异。

**结论（硬性）**：
1. **压缩音频只动文件，绝不重跑转写**。库内音频与已定稿转写稿**不是逐字对应**的关系。
2. **产物文本不能当 A/B 判据**。要证明「音频瘦身无害」，只能固定**唯一变量 = 音频规格**，
   且必须冻结 VAD 切点（或直接只比规格、不比文本）。
3. 如果哪天必须复用转写稿，**在稿子里标注对应音频版本**，别假设它能重现。

**顺带实测（供参考，别当判据）**：瘦身音频跑转写**快约 19%**
（原音频 383s / 6.77× 实时 ↔ 瘦身 322s / 8.15× 实时）。

## 6. 说话人分离（diarization）的边界

- 可用的声纹嵌入模型是 **`campplus_sv_zh_en`** —— **只覆盖中文和英文**，其它语种不可靠。
- 实测**命中率**：多数期可用，个别期只有 **56%**（贾鹏期，四方以上对谈）。
  四方对谈建议只做 **2 轨**（主持 vs 嘉宾群），做 4 轨命中率下降明显。
- 独白类内容（单人主讲）需显式标注「说话人标注说明（可靠性低）」，别让读者以为分轨可信。
- **并发配方**（2 核 CPU / 15.8 GB 内存下的最优点）：
  `*_NUM_THREADS=1` × 5 并发 + `--parallel 8`，单期 27–30 分钟。

## 7. 跨平台判重（本轮新增，重点）

**规则**：*"同一博主在不同平台（B站 / YouTube / 小宇宙）内容相似乃至一致时，也视为重复，不再走流水线。"*

**实现（双判据，宁漏不误）**：

| 判据 | 作用 | 阈值 |
|---|---|---|
| **时长** | 主判据（同一期录音时长几乎一致） | 差异 ≤ 3%，**几乎相同（≤15s）时放宽标题阈值** |
| **标题相似度** | 副判据（跨平台标题会改写） | 时长几乎相同 → 0.35；否则 → 0.55 |

**保守原则**：**漏判只是多跑一遍，误判合并会丢真内容** → 阈值偏保守。

### 三个实测踩坑

**坑①：播客页没有时长，判重直接失效。**
小宇宙（xiaoyuzhou）页面需要解析内嵌 `__NEXT_DATA__` 才有 `duration` / `pubDate` / `eid`；
只抓标题的旧实现 → 同一期在小宇宙冒出来会被当成新内容。

```python
import json, re
m = re.search(r'<script id="__NEXT_DATA__"[^>]*>(.*?)</script>', html, re.S)
data = json.loads(m.group(1))     # 递归找 dict 里同时有 duration/title/eid 的节点
```

**坑②：库内判重的时长容差必须放宽到 6%（不是 3%）。**
同一期在 B站是**视频版（带片头片尾）**、在小宇宙是**音频版**：
实测量化 —— 世博期 B站 **54:38** vs 小宇宙 **52:21**，**差 137 秒 = 4.2%**，
3% 容差**判不出来** → 会被当成新内容再走一遍流水线。

**坑③：命中口径必须只认标题。**
巡检原先用「标题 + 描述」匹配关注话题。接上播客源后实测：5 条「命中」里 **4 条是描述里的泛词**
（`落地` / `泡沫` / `李飞飞` / `RL`），**全都不是具身题材**。
→ 改成**标题命中才算命中**，描述命中降级为 `topics_matched_weak`（只进 JSON 留档，不告警）。

### 顺带发现：表格里的 wikilink 会被普查脚本误判

知识库里有 47 个「幽灵链接」是我的普查脚本自己造的假象：
**Obsidian 表格里 `[[目标\|别名]]` 是正确的转义写法**（不转义的 `|` 会破坏表格），
脚本把 `\|` 当成了链接目标的一部分。**写分析脚本时先把 `\|` 还原成 `|` 再解析。**

### 副产物：判重需要「库内每一条的时长」

库内条目缺时长（原始登记表里没写）→ **无法参与判重**（实测漏判 1 期真实重复）。
修法：缺时长就按 bvid 查一次 B站 API 并**落盘缓存**（`state/media-dedupe-dur-cache.json`），
之后零网络请求。缓存删了会自动重建，只是多几次请求。

## 8. 删原件前的安全流程（三步，不可省）

1. **逐文件校验**：新文件存在 + 能解码 + 规格符合 + 体积更小 + 时长一致；
2. **写重下清单**（manifest）：记录每个被删文件的来源 URL / bvid，以便重建；
3. **再删**。

```bash
# 校验脚本踩过的坑：文件名带 .h264. 这类中间标记时，配对会失败
base=$(basename "$f" | sed 's/\.h264\././')      # 剥离标记后再配对
```

**实测**：备份清理释放 **2.82 GB**（音频备份 1385 MB + 视频备份 1263 MB + 其它 193 MB + 临时 51 MB）；
同一轮把 `cache/scratch` 从 **3.0 GB → 82 MB**。磁盘仍有 675 GB 空闲。

4. **跨平台判重的 seen 键不共享命名空间**（B站 = `bvid`，小宇宙 = `xyz:<eid>`）→
   同一期跨平台会被各记一次，靠「对库判重」兜底。若要彻底统一，需建跨平台 episode 指纹表。
5. **代理是网络地址，不是凭据**；但「哪些站必须走代理」**因站而异**（实测：github / google 直连不通，
   `example.com` 直连通），所以策略是**全局走代理**（分流由代理侧规则负责）。
